# Personal OS 事务模块设计

日期：2026-10-03

状态：设计提案，尚未实施或部署数据库变更。

## 1. 目的与领域边界

事务管理个人要完成的事情和承诺。用户当前的主要场景是论文、求职和公务员考试准备，后续生活事务也使用同一套模型。

一级导航为首页、财务、事务和设置。事务与财务并列；学习方法、专注计时、中断恢复属于事务领域中的可选能力，不设独立一级模块。

成功标准：用户能把事情记录下来，归入项目，区分截止日期和执行安排，查看待办与项目进展，并完成或重新安排任务。系统结构应在用户结束当前考试或论文阶段后继续适用。

## 2. 核心概念

| 对象 | 定义 | 示例 | 所属关系 |
| --- | --- | --- | --- |
| 项目 Project | 有明确结果、需要多个行动推进的事情 | 完成论文返修、准备本次国考、完成本轮求职 | 一个项目有多个任务 |
| 任务 Task | 可以执行和完成的具体行动 | 修改论文第三节、完成一套申论练习、投递某个岗位 | 可属于一个项目，也可独立存在 |
| 日程 Event | 在特定时间发生的活动或约定 | 面试、考试、导师会议 | 可关联项目，后续独立建模 |
| 目标 Goal | 希望达成的结果与衡量方式 | 获得符合要求的工作机会 | 后续关联项目，不是任务状态 |

“论文、公考、求职”作为用户创建的项目示例，不硬编码为模块、固定分类或默认数据库记录。长期重复的领域可以日后支持领域分类，不影响项目和任务的关系。

任务的截止日期表示最晚完成日期；安排时间表示打算执行的时段。改安排时间不会自动改截止日期。任务完成表示行动完成，不等于日程已经结束。

## 3. 分阶段范围

### 第一阶段：项目与任务

- 项目新增、编辑、暂停、恢复、完成和归档。
- 任务新增、编辑、完成、重新打开、取消，以及项目归属调整。
- 每个任务可填写截止日期和安排时段，两者均为可选项。
- 独立任务无需先创建项目。
- 事务列表、项目列表、项目详情和任务表单。
- 展示真实数据库数据；新模块没有数据时显示真实空状态。
- 保持现有暗色设计和桌面／移动端响应式。

第一阶段不加入专注计时、学习打卡、自动拆解计划、重复任务、子任务、看板拖拽、系统通知和日历平台同步。

### 第二阶段：日程

新增独立日程对象；时间视图同时读取任务安排和日程。第一阶段不为已安排的任务创建重复 Event 记录。考试和面试这类活动在第二阶段进入日程，准备活动仍为任务。

### 第三阶段：Agent 事务操作

复用首页入口和千问接入，新增事务意图与独立的类型校验／确认处理。用户可通过一段话提出多项任务，预览后确认写入。项目、任务的人工操作先稳定，再增加自然语言创建和查询。

目标、跨领域关联和主动建议在事务实际使用后另行设计。

## 4. 第一阶段页面

### /affairs：事务列表

次级导航为“任务”“项目”。默认打开任务列表。

任务列表提供以下视图，它们查询同一任务对象，不生成额外记录：

- 当前：未完成、未取消的任务，可按项目和状态筛选。
- 已完成：完成任务的历史。
- 已取消：取消任务的历史。

当前视图中展示逾期、今天和其他待办分组。逾期由截止日期判断；今天包括安排时段与今天相交的任务，以及今天截止的任务；同一任务只显示一次，逾期分组优先。没有日期的任务保留在其他待办，系统不把它们自动安排到今天。

行信息：任务标题、所属项目或“独立任务”、状态、截止日期、安排时间。优先级在表单和详情中提供，列表用轻量标记展示。

任务列表支持真实数据库确认后的完成、重新打开和取消；成功后刷新相关任务和项目进度。

### /affairs/projects：项目列表

展示用户项目、状态、目标结果、截止日期、未完成任务数量和完成进度。可筛选进行中、暂停、完成、归档项目。

项目任务进度为完成任务数／非取消任务总数，无任务时显示“尚无任务”。进度只代表任务完成情况，不推断论文、求职或考试结果。

### /affairs/projects/[projectId]：项目详情

展示项目信息、关联任务、未完成与已完成任务，并提供编辑项目、添加任务入口。新增任务自动带入该项目。

### 表单路由

- /affairs/projects/new
- /affairs/projects/[projectId]/edit
- /affairs/tasks/new
- /affairs/tasks/[taskId]/edit

任务表单：标题、说明、项目、状态、优先级、截止日期、安排开始时间、安排结束时间。

项目表单：名称、目标结果、说明、截止日期。项目状态操作单独提供，避免编辑元数据意外改变状态。

## 5. 数据模型

使用独立的新表，最终 migration 前检查远程是否存在同名对象。现有财务表、RPC 和 View 不修改。

### affairs_projects

- id：uuid，项目标识。
- user_id：uuid，绑定 auth.users。
- name：text，1–200 个字符。
- outcome：text，可空，最多 1000 个字符，描述明确结果。
- description：text，可空，最多 10000 个字符。
- status：active / paused / completed / archived，默认 active。
- due_date：date，可空。
- completed_at：timestamptz，可空。
- revision：整数，默认 1，用于更新冲突检测。
- created_at、updated_at：timestamptz。

### affairs_tasks

- id：uuid，任务标识。
- user_id：uuid，绑定 auth.users。
- project_id：uuid，可空。
- title：text，1–200 个字符。
- description：text，可空，最多 10000 个字符。
- status：todo / in_progress / waiting / done / cancelled，默认 todo。
- priority：low / normal / high，默认 normal。
- due_date：date，可空。
- scheduled_start_at、scheduled_end_at：timestamptz，可空。
- completed_at：timestamptz，可空。
- revision：整数，默认 1，用于更新冲突检测。
- created_at、updated_at：timestamptz。

项目与任务的 user_id 必须一致，以复合外键和 RLS 保证。任务所属项目改变时，也必须验证目标项目归属。

安排时段允许两字段同时为空；填写时必须同时存在且结束晚于开始。未来日期是事务中的有效输入。跨天任务允许安排，不限制在同一天。

截止日期保留 date 语义，页面按 Asia/Shanghai 判断今天／逾期；安排时段在数据库保存绝对时间，输入和显示采用 Asia/Shanghai。未设置日期和时段时保存 null，不自动生成。

## 6. 状态与更新规则

- 任务完成时由数据库设置 completed_at；重新打开时清空。
- 取消任务保留历史记录，不计入项目任务进度的分母。
- 项目暂停和恢复保留所有任务；不自动重排任务或取消日期。
- 完成项目时若仍有未完成、未取消任务，返回明确提示；用户处理这些任务后再完成项目。
- 已完成或已归档项目保持可读；恢复项目后可继续添加或修改关联任务。
- 归档项目不删除任务，事务列表默认隐藏归档项目的任务；项目详情仍可查看。
- 第一个版本保留任务取消和项目归档，不提供物理删除入口。
- 更新请求携带 revision。版本不一致时返回冲突，提示重新加载，不覆盖其他页面已保存的更新。
- 创建请求携带稳定的 request_id，作为记录 id 使用；重复请求只在用户和请求内容一致时返回原记录，否则返回冲突。

## 7. 数据访问与认证

沿用 Next.js 15 App Router、Supabase SSR、publishable key、Auth cookie 与 RLS。事务路由自动纳入现有 middleware 的认证保护。

页面 → affairs service → typed queries / mutations → Supabase SSR client。

建议结构：

```text
src/lib/affairs/
  types.ts
  queries.ts
  adapters.ts
  service.ts
  validation.ts
  mutations.ts

src/features/affairs/
  types.ts
  components/
    affairs-tabs.tsx
    task-list.tsx
    project-list.tsx
    project-detail.tsx
    task-form.tsx
    project-form.tsx
    affairs.module.css

src/app/affairs/
  layout.tsx
  page.tsx
  actions.ts
  projects/...
  tasks/...
```

所有表启用基于 auth.uid() = user_id 的 RLS，anon 无业务读写权限。写入通过 authenticated 可调用的 SECURITY INVOKER RPC，验证归属、版本和状态，在单次事务内提交。RPC 使用明确 search_path，并撤销 public/anon execute。

Server Action 再次验证 getClaims()；查询／更新共用当前操作的 SSR client；UI 仅在确认保存成功后更新。创建时保留 request_id 和提交内容，避免结果不明确时产生重复任务。

数据库类型进入统一 Supabase Database 类型后供事务查询使用；事务领域类型不引用 finance 的业务模型。详细类型迁移路径在实施计划中列明。

## 8. 页面、失败与空状态

- 数据库未部署：显示“事务模块尚未完成数据库配置”，不当成没有任务。
- 数据库真实空结果：显示创建项目和独立任务入口。
- 查询失败：显示可重试错误，保留具体错误在服务端，不回退 mock。
- 写入失败：保留表单输入；版本冲突要求重新加载最新记录。
- 结果不明确：保留原提交标识与内容，提示核对或重试原请求。
- 未登录：由现有认证链路转入登录页，不索要密码或数据库密码。
- 无权访问或不存在的项目／任务：返回 404，不泄露其他用户数据。

## 9. 验收

1. 无日期、无项目的独立任务可保存并在当前视图找到。
2. 用户创建论文项目，添加两项任务，完成一项后真实进度显示 1/2。
3. 任务同时有截止日期和安排时间；调整安排时间后截止日期保持原值。
4. 未来安排和跨天安排有效；截止日当天不算逾期。
5. 完成任务可重新打开，取消任务保留历史；未完成任务全部处理后可完成项目。
6. 暂停、归档、恢复项目的状态和任务显示规则符合本设计。
7. 创建请求重复提交不会创建第二条记录；修改冲突不会覆盖新版本。
8. 未登录和其他用户不能访问或更新记录，不能关联其他用户的项目。
9. 主导航和命令菜单可进入事务；移动端列表、表单可用。
10. Finance 和现有 Agent 财务操作继续通过现有测试；第一阶段不改变其解析行为。
