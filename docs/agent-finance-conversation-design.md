# Agent 财务交互式录入设计

日期：2026-10-11

阶段：书面设计，待用户审核；尚未实施。

位置：沿用仓库现有 `docs/agent-*-design.md` 文档组织，不改 `.gitignore`。

## 1. 目标与范围

用户只需说交易事实，Agent 记住待处理内容，合理建议分类，只追问不能安全确定的信息。后续的“情侣小荷包”应回答上一笔的付款账户问题，而不是变成一条缺少金额的新指令。

第一版升级财务录入：已有的支出、收入、转账（包括储蓄、投资、还款用途），支持一段话包含多笔，支持多轮补充与保存前修改。保留当前暗色首页、千问供应商、真实账户/分类/预算读取及现有 Finance RPC。

本期不做通用聊天、财务分析问答、已保存交易的 Agent 编辑/删除、长期记忆、自动创建账户/分类、跨设备对话同步、数据库 migration。事务录入保留现有能力，暂不升级为多轮事务编辑；不能因此破坏事务预览、重复检查和确认流程。

## 2. 已核实的现状

- `agent-workspace.tsx` 保存可见消息，但调用 `action(message)` 只发送最新一句。
- `agent-actions.ts` 对每一句先做领域识别，再单独解析。领域识别和财务解析都没有上一轮草稿或待回答问题。
- `orchestrator.ts` 每次重新生成 `draftId`；收入、转账另有 `requestId`，支出没有。
- `transaction-preview.tsx` 的保存结果是卡片局部状态。财务的保存中/结果不明状态尚未像事务一样反馈给工作区的统一保护机制。
- `getAgentFinanceOptions()` 使用同一个 Supabase client，并发读取真实账户、支出分类、收入分类和预算分类；只返回启用选项。分类的默认预算关系已可读取。
- 现有 `confirm.ts` 会再次校验真实选项，并调用现有 mutation 层。收入、转账支持请求标识，普通支出 RPC 不支持请求标识。

这些事实支持“有状态草稿 + 受约束的增量更新”，不能把截图中的失败简单归因于千问能力，也不能只靠拼接完整聊天记录解决。

## 3. 核心交互

示例中的账户和分类名仅用于说明；生产候选全部来自真实读取，不硬编码。

1. 用户：“午饭花了20。”
2. Agent：建立一笔支出草稿，金额 20；日期默认本次记录时的北京时间；建议真实可用的餐饮分类及其默认预算。只问：“这笔用哪个账户付的？”并展示实际账户选项。
3. 用户：“情侣小荷包。”或点击对应账户。
4. Agent：更新同一笔草稿，不丢金额、日期、描述或分类；提示“已补充付款账户，请确认这笔记录。”
5. 用户检查同一处预览，点击“确认并记录”；此时才调用 RPC。

普通缺项不是报错。不再用“未检测到明确交易指令”或一大段缺项警告回复正常补充。

页面保留简短聊天过程，但财务只维护一处当前预览区域。新回复更新该区域，不在每条历史消息下面复制整套可提交卡片。多笔草稿显示稳定编号和各自确认按钮；本期不新增“一键批量保存”，避免暗示多笔 RPC 原子性。

预览中的账户、分类、预算和日期可点击修改，使用现有风格的紧凑控件；不强迫用户为确定的字段再进入手动交易页。所有操作支持键盘，移动端单列，状态提示可被辅助技术读取。

## 4. 信息推导和追问口径

| 字段 | 处理规则 |
| --- | --- |
| 金额 | 必须有准确金额；不从“几十”“大概”推造数字，不合并多笔金额。 |
| 交易类型 | 从明确表达判断支出/收入/转账；没有事实依据时问方向。 |
| 付款/收款账户 | 名称明确且唯一匹配真实选项可采用；否则追问。不得依据常用程度、余额或历史习惯自行猜测。 |
| 转账两端 | 必须确定转出、转入及方向；沿用资产/负债、币种和用途校验。 |
| 分类 | 从真实候选建议语义明确的分类，并在预览标为“建议”；用户可直接修改。存在多个合理候选时追问，不以模型自报置信度当作校验。 |
| 支出预算 | 显式“不计预算”优先；其次用户明确预算分类；否则沿用真实分类的默认预算。不得因缺少当月预算而丢掉预算归属。 |
| 转账预算 | 沿用现有用途与 bucket_kind 规则；普通转账不计预算，不改变储蓄/投资/还款口径。 |
| 日期/时间 | 未提供时默认创建该草稿时的北京时间，预览标“默认记录时间”；不反复追问。用户明确的日期优先。 |
| 描述 | 从用户交易原话提炼，不虚构商户或用途。若只给账户和金额而完全没有用途，可用中性“支出/收入/转账”描述，不为可选描述阻塞。 |
| 备注 | 可选，未提则为空。 |

时间统一使用 `Asia/Shanghai`。默认时间在草稿首次创建时固定，跨午夜继续回答不能使日期漂移。用户明确过去日期但没有时刻时采用该日 00:00，并标“未指定时刻”；涉及不明确年份或有多个可能日期时追问。保留现有不接受未来已发生财务交易的验证，非法日期不能静默改为今天。

账户的自由文本缩写只能生成候选建议：没有唯一可信匹配时展示真实名称让用户选择。不新增别名表，不长期记忆昵称。点击账户按钮传递实际 ID；服务器验证 ID 仍属于当前用户的启用选项。

字段保留来源：用户明确、模型建议、系统默认。纠正分类后，未被用户明确指定的预算默认随真实分类更新；用户明确预算或“不计预算”不被建议覆盖。用户取消“不计预算”后恢复默认/显式预算规则。

问题一次只问一个主题。处理顺序：交易类型与指代 → 准确金额 → 账户/转账两端 → 分类 → 确实必要的用途或预算歧义。多个未保存条目缺同一账户时可问“这几笔都是同一账户支付吗？”；只有用户明确答“都是”才批量应用。

## 5. 草稿与回合状态

新增明确的财务会话状态，不把可见聊天记录或模型输出当作权威账本。

- `conversationId` / `batchId`：当前财务会话及预览批次标识。
- `revision`：草稿更新版本；`turnId`：一次补充请求标识。
- 每笔保留稳定 `draftId`、展示序号、交易字段及来源、原始输入、校验问题。
- `pendingQuestion`：问题类型、字段、目标 draftId 集合、实际候选及提问文本。
- 只有账户、还没有交易方向时保留一个不允许提交的 `intentSeed`（已知账户与原话）；方向明确后才创建具备 expense/income/transfer 类型的交易草稿，不强行猜出一笔支出。
- 每笔生命周期：`editing`、`ready`、`saving`、`saved`、`uncertain`、`discarded`。就绪由服务器规则计算，不能由模型决定。
- 保存结果与 `entryId` 属于会话状态，不再只藏在容易重挂载的卡片组件中。

更新只允许当前未提交条目。模型不能改变生命周期、请求标识、保存结果、候选列表、用户身份或已保存记录。保存中和结果不明条目冻结；已保存条目只显示只读回执，不受“都是”“改成”等后续回答影响。

普通编辑保留 draftId。收入/转账的 requestId 在首次尝试保存前可由服务器更新为当前确认快照的新标识；一旦尝试保存即与该快照绑定，不再用于另一个 payload。明确回滚后修改产生新确认标识；结果不明绝不修改旧快照或换标识重试。支出仍不向不支持该参数的 RPC 传 requestId。

## 6. 回答与新增交易的区分

有财务待处理草稿或 intentSeed 时，优先进入会话补充处理，不把“情侣小荷包”交给仅识别新指令的分类器。没有上下文、仅输入一个唯一匹配的真实账户名称时，建立 intentSeed 并问要记支出、收入还是转账；其他无事实依据的零散文字不自动变成交易。

受约束的解析结果允许：

- `patch`：对指定未提交 draftId 修改有限交易字段。
- `append`：用户明确增加交易事实时追加，不重新生成已有交易。
- `clarify`：指代或含义不足，暂不改变字段，提出必要问题。
- `route`：明确属于其他领域，保持财务草稿并交给既有入口。

“第二笔不计预算”只修改展示序号 2 对应的未提交条目。“都是微信付的”只作用于当前批次未提交且适用的支出，不把转账两端或收入账户一起改掉。“这笔改成20”有多个可能对象时先问哪一笔，不默认第一笔。用户明确只回答当前问题时不能生成 append。

用户可明确追加“另外买了咖啡15”。服务器为新增条目分配 ID，保留原有编号；每批次累计最多 20 笔（包括已保存和已取消），不自动合并相似描述或相同金额。取消未提交条目不重新编号，避免“第二笔”指错对象。全部条目结束后可开启新批次，旧批次只保留只读结果。

金融草稿存在时，明确的事务新指令可以走原有事务流程，但不得把财务追问上下文混入事务模型。财务或事务任一预览保存中/结果不明时，共享工作区提交保护。单句话同时要求两个领域写入仍要求分开发送，不悄悄只做其中一部分。

## 7. 服务端数据流与职责

数据流：用户文本/选项操作 → Server Action 验证 Auth 和输入 → 读取真实 Finance 选项 → 会话解析/确定性选项处理 → 校验并应用 patch → 重新计算就绪与下一问题 → 返回更新预览。此链路不执行财务写入。

候选按钮提交结构化 `selection`，包含问题、版本、目标和实际候选 ID；服务器完成验证和确定性更新，不为点击已有选项再请求千问。自由文本回合发送最新输入、必要的待处理草稿、当前问题及最近最多 6 条用户文本（合计最多 6000 字符）作为上下文，不把无限完整历史、余额、已保存交易详情发送给模型。

沿用单条输入最多 4000 字符；会话输入 JSON 最多 40000 字符，超限拒绝且保留现有状态，不悄悄截掉交易。每笔描述和备注仍最多 1000 字符，金额及小数精度沿用现有 Finance 验证。每笔 rawText 保留首次创建时的原始交易输入，不拼接无限补充历史；实际提交字段以用户最终确认的快照为准。

第一版状态由当前浏览器工作区持有，服务器每轮完整验证输入、身份、大小、字段和真实选项。客户端的 revision 与已保存标志用于协作和防旧响应覆盖，不是数据库权限或可信审计证据。Vercel 进程内存不能用作持久会话存储。本期不建立服务端会话表。

首页 Server Component 通过现有 SSR client 的 `getClaims()` 取得已验证用户标识，传给工作区，用于首次恢复保护信息；只传用户标识，不传 token，不预加载全部财务候选。每个解释/确认 Action 仍独立验证当前用户，主体不一致时拒绝继续旧会话。

保持单个 Action 调用复用一个 Supabase server client。会话活跃时不再先调用无上下文领域分类器；无会话的新消息继续保留已有领域分流。模型通过严格 JSON Schema 返回增量意图，服务器拒绝未知字段、非法 ID、无法对应的目标及不允许的更新。拒绝一次响应时保留整个原草稿，不能部分应用合法字段。

应用层负责：

1. 身份、输入与候选验证。
2. 稳定标识、生命周期与版本。
3. 默认时间、分类默认预算关系和校验规则。
4. patch 应用及下一问题生成。
5. 保存冻结、结果和 Finance 刷新。

模型只负责理解语义、提出允许字段的候选更新，不自行决定保存、修改数据库或跳过验证。

## 8. 保存、重试和恢复边界

每笔仍通过“确认并记录”按钮保存；聊天中的“保存”“确认”只定位到可确认预览，不直接写入。不新增模型工具执行权。确认提交当前不可变快照，重新验证 Auth、真实账户/分类/预算及现有金额、时刻、币种、方向规则，然后复用原 mutation/RPC。

- 成功或预算警告：显示真实 entryId 对应结果，冻结该笔并刷新 `/finance`，不能为了刷新失败重新提交。
- 明确未写入：保留草稿，解释失败；修正或重试前重新校验真实选项。
- 网络异常或结果无法确认：置为 uncertain，锁定该批次和共享 Agent 提交入口，提示到交易列表核对；不自动重试、不重新解析原话、不允许丢弃后直接复制成新交易。

提交期间禁止并发解释、修改或新建另一笔。快速双击只能发起一次请求。旧 turnId/revision 的延迟结果不覆盖新预览，重复收到同一解释响应不追加第二份草稿。

会话正文与未提交草稿仅保留在工作区内存，刷新后不承诺恢复聊天；刷新前提示未保存内容。为避免保存中刷新解除保护，只在当前标签页 sessionStorage 持久化最小提交保护信息：服务器验证后的用户标识、batchId、draftId、requestId（若有）、提交时间、类型和状态。不存金额、账户名、正文、密码、API key 或 token。存储失败则不发起写入。

初次恢复和保存前必须核对当前已验证用户；不属于当前用户的保护信息不能作为其交易状态。不从浏览器缓存取得或推断 Auth session。保护标记在 RPC 成功/明确回滚后清除；刷新中断或未知结果保持核对提示。用户核对后可明确结束该待核对记录，但不提供原交易“一键重试”，也不宣称自动确认了结果。

这是前端防误操作，不是数据库级 exactly-once 保证；清除浏览器数据、跨标签页或人为重复录入仍可能重复写入。收入/转账沿用数据库现有幂等性；支出完善幂等性属于后续独立数据库设计，本期不偷偷增加 migration 或承诺所有重复都能拦截。

## 9. 组件和文件边界

新增或调整文件由下一步实现计划细化；职责范围固定如下：

| 文件 | 职责 |
| --- | --- |
| `src/lib/agent/conversation/types.ts` | 会话、问题、patch、来源与生命周期契约。 |
| `src/lib/agent/conversation/validation.ts` | 不可信会话/选择/模型更新输入校验，复用财务字段验证。 |
| `src/lib/agent/conversation/state.ts` | 纯函数状态更新、稳定目标、版本检查、冻结规则。 |
| `src/lib/agent/conversation/questions.ts` | 缺项排序和真实候选追问，不依赖组件或数据库。 |
| `src/lib/agent/conversation/orchestrator.ts` | Auth 后调用的会话编排，读取选项、模型建议、校验及问答。 |
| `src/lib/agent/qwen.ts` / `schema.ts` / `types.ts` | 添加会话增量解析与兼容类型，不修改供应商密钥配置。 |
| `src/app/agent-actions.ts` | 会话 Action、已验证用户边界、继续复用确认 Action。 |
| `src/app/page.tsx` | 向工作区提供已验证用户标识，隔离提交保护信息，不信任未经验证的 getSession()。 |
| `src/features/agent/agent-workspace.tsx` | 单一当前预览、短消息历史、Finance/Affairs 共享保护；拆出会话控制逻辑，避免继续堆在一个组件中。 |
| `src/features/agent/finance-conversation-preview.tsx` | 当前批次及只读回执展示，单笔确认。 |
| `src/features/agent/clarification-question.tsx` | 紧凑问题、真实候选按钮、键盘交互。 |
| `src/features/agent/transaction-preview.tsx` | 从会话接收保存状态与回调，增加保存前字段编辑，不自行拥有唯一保存结果。 |
| `src/features/agent/submission-protection.ts` | 标签页最小提交保护存储和已验证用户隔离。 |
| `src/features/agent/agent-workspace.module.css` | 沿用设计语言的局部响应式样式，不重设计首页。 |
| 对应现有与新增测试 | 模型契约、状态、追问、Action、确认保护与 UI 回归。 |

需要复用/提取现有 `orchestrator.ts` 的候选映射与校验，避免单轮和多轮出现两套口径。`confirm.ts` 和 Finance mutations 只为必要的验证复用做小范围调整，不改变现有 RPC 参数或账务规则。页面/组件不得出现直接 Supabase `.from()` 查询。

## 10. 验收标准

必须用固定千问响应夹具和真实结构选项夹具覆盖，不自动用生产账号或实际财务数据调用模型/写入数据库：

1. “午饭花了20” → 问付款账户 → “情侣小荷包”：同一 draftId，只有一笔，20 不变，建议分类和默认预算保留。
2. 一句话多笔 → “都是微信付的” → “第二笔不计预算”：作用范围正确，编号稳定，不改已保存项。
3. “改成建行”“第二笔改成25”“昨天的”：定向更新；不明确对象则只问，不改错记录。
4. 真实分类不存在或有多个合理分类：不虚构 ID，展示必要选择；用户明确预算不被默认覆盖。
5. 默认北京时间、跨午夜补充、过去日期缺时刻、非法日期与未来日期：不漂移、不静默修正。
6. 收入资产账户限制、转账两端/币种/用途限制、普通转账无预算：现有口径不变。
7. 点击候选不调用千问；没有待处理草稿却只说账户时做必要方向追问，而非要求一次补齐全部字段。
8. 超时、非法 JSON、提示注入、未知 ID、越权目标、陈旧版本：不写入、不破坏已有草稿、不接受模型控制状态。
9. 快速双击、保存中补充、成功后纠正、结果不明后重发、刷新/存储失败/用户切换：按上述保护边界处理。
10. 一个已保存条目与其余待补充条目共存：保存结果保留；只在确定性成功/失败后继续，不能重复提交该条目。
11. 事务原有领域分流、预览、父子关系、重复检查及保存保护回归通过。
12. 类型检查、lint、全量现有/新增测试和生产 build 通过；本地浏览器验证多轮输入、按钮补充、保存前编辑、窄屏与键盘。真实写入测试需用户明确提供测试交易并授权，不能拿现有消费做自动重复录入。
