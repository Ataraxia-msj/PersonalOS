## 1. 用户目标与边界

用户实测一期后提出：新增入口分散、没有收集箱、打开只见主线而没有完整 TODO，不能顺着主线查看全部项目和行动。用户已接受“统一新增、先收集后整理、打开就看到 TODO、主线逐层展开”。

用户随后提供两张首页批注图：顶部现有“事务”标题/操作区改为事务数据总览；在主线成长整个区域下面、金币规则上面增加 TODO List。以下布局以这两处批注为准，替换此前侧栏式工作台和贡献图后置建议；不是授权改动其他页面或提前实施。

用户进一步要求：网页不展示无关紧要的信息，注意可读性和交互性。优先减少常驻说明和操作噪声，必要的确认、未知结果和错误提示仍保留。此约束应用于本次事务改版，不据此重做 Finance 或全站功能。

用户接受简化职责：工作台用于日常执行；项目页用于查看全部项目、管理阶段成果与历史；完整行动页保留但不占顶部导航，通过工作台行动清单的“查看全部”进入。

成功的日常路径：想到事情 → 一句话收集；想执行 → 直接找到未完成行动；想看长期方向 → 展开主线、项目和行动。不要求先把事情分类清楚，不要求给每件事安排今天或执行时间。

保持一期金币、项目阶段成果、完成/重开/误完成撤销、商店和惩罚规则。核心任务完成 +1，普通任务 +0，手动惩罚 −1；收集、整理、创建、归属变更不发币、不生成贡献。计时奖励仍未接入。Finance、Agent、Notes 不在本次范围。

本次只增加捕获与组织能力，不引入四象限、自动重要性排序、每日承诺、连续打卡惩罚或时间块。

## 2. 已核实的现状

- `progress-dashboard.tsx` 只选出每条主线的 focusProjectId 项目；只展示它最多三条未完成核心行动，没有完整层级入口。
- `task-list.tsx` 默认筛选 `!projectId && !isCore`，需要手动切“全部行动”才能看到项目任务和独立核心行动，切换后页标题仍是“零散事务”。
- 现有主线 → 项目 → 行动外键关系已经成立，不需要复制或重建已有业务对象；项目可以不属于主线，行动可以不属于项目。
- 有统一 query/service/adapter/Server Action、原子 RPC、owner RLS、revision 和幂等请求。继续沿用这些边界。
- 当前没有独立收集状态，不能把 `project_id IS NULL` 当作收集箱，也不能把普通任务当作“未整理”。

## 3. 页面与信息层级

| 路由 | 改版后含义 |
| --- | --- |
| `/affairs` | 工作台：完整组织入口 + 默认未完成行动 |
| `/affairs/inbox` | 收集箱：未整理、已整理、已丢弃 |
| `/affairs/tasks` | 完整行动列表：由工作台“查看全部”进入，默认未完成，保留历史筛选 |
| `/affairs/projects` | 项目管理：全部项目、阶段成果与状态历史，保留直接详情入口 |
| `/affairs/projects/[projectId]` | 项目成果、阶段、行动、进展，保留已有功能 |
| `/affairs/shop`、`/affairs/coins` | 商店与账本，业务行为不变 |

事务导航最终统一为“工作台 / 收集箱 / 项目 / 奖励商店 / 金币记录”，不显示“行动”页签。仅减少导航入口，不删除 `/affairs/tasks` 及已有创建、编辑路由或收藏链接。访问完整行动页时在该页提供明确的“返回工作台”，导航仍保持这五项，不伪装成项目页选中状态。不新增与现有项目详情竞争的第二套详情对象。

### 3.1 工作台

保留当前纵向页面和暖黑/米白/橙色视觉，不改成固定左侧树、右侧列表。页面顺序明确为：事务数据总览 → 推进轨迹 → 主线与项目（含可展开项目与行动）→ 行动清单（TODO List）。TODO 放在批注箭头指定的位置，即整个组织区域结束处、原金币规则之前。金币规则不再是常驻大区块，按需从帮助或相应商店/账本操作查看。

顶部红框区域不再展示内容区大标题“事务”，也不新增“数据总览”等替代大标题。操作入口合并至事务导航右侧，导航下直接展示四项真实数据；收掉原标题占用的空白。四项指标按已选效果图保留，统计口径供用户审核：

| 指标 | 口径 |
| --- | --- |
| 待办行动 | 本人的 todo / in_progress / waiting 正式任务总数，含核心、普通、项目、独立及需恢复项目的任务；排除 done / cancelled，不含收集项 |
| 进行中项目 | 本人的 status=active 项目数，含无主线项目；paused / completed / archived 不算 |
| 近7天完成 | 上海业务日期今天及前六天内完成、completed_at 不晚于本次服务端 now，且当前仍为 done 的任务数；核心和普通都算，是任务数而非重复完成次数 |
| 金币余额 | 现有 vw_affairs_coin_balance 返回的当前真实余额，支持负值，非历史回执或当前页流水加总 |

总览始终是全事务数据，不随着某条主线/项目或 TODO 筛选改变，不把它包装成主线成长率。完整读取的任务/项目在 service 层归纳计数，UI 只展示结果；禁止用截断列表、当前展开节点或分页的一页计算总量。

`＋新增` 放在顶部右侧，保留“提交进展”作为次级操作。金币指标链接商店，不再重复放一份同义余额徽章；待办指标可定位下方 TODO 并切回“全部未完成”。收集箱 pending 数量作为收集箱入口徽标单独展示，不将其混进待办数。

桌面总览指标同排，手机两列排布；热力图保留现有可横向滚动行为，手机不得造成整页横向溢出。主线卡片/层级与 TODO 都全宽纵向排列。主线较多时用户可折叠，顶部待办入口可直接定位，避免寻找任务必须另进一页。

TODO 位于整个“主线与项目”区域之后，是唯一的全局行动列表，不为每条主线复制独立任务记录。默认全部未完成，不隐藏普通或独立行动；在主线内选择项目/行动只是可选范围过滤，默认不会要求先选择关注项目才显示 TODO。标题旁提供“查看全部”链接进入 `/affairs/tasks`；该入口表示完整行动管理页，不等同于首页的“全部行动”范围筛选。贡献图保留第二个区域，解释和规则按需展开，不挤占 TODO 的常规阅读。

### 3.1.1 可读性与交互约束

- 每个区域只保留清晰标题、真实内容、必要的状态/计数和相关操作。不重复 AFFAIRS 标签、营销式副标题、金币规则、技术术语和跨页重复说明。
- 未上线的计时功能不在正常工作台展示奖励规则或不可用按钮；开发范围写在文档中，不变成用户每次打开都要读的提示。
- 四项总览使用短标签和易读数字；具体统计口径放在可聚焦的帮助入口，不用长段文字占据首页。
- 主线强调名称和项目关系；项目强调成果/阶段进度；行动强调标题、状态、归属和完成入口。长说明、历史与次要操作按需展开，折叠不改变对象可访问性。
- 行动主操作直接可见，编辑、历史及更改状态等可归入明确的次级菜单；不可仅依赖 hover、没有名称的图标或颜色区分。键盘和触屏同样能到达所有操作。
- 展开/收起、范围与状态筛选必须有可见且程序可读的选中反馈；主线、项目、行动的标题层级和缩进一致，标题/正文/辅助信息有稳定区别。
- 手机保持足够点击区域和清楚的行间距，不把所有状态和日期挤成一行；日期为空就不显示占位噪声，常见完成操作不应被次要按钮推到屏幕外。
- 输入只要求本次操作必需字段；其他字段明确可选、可展开。成功、失败、保存中和未知结果有简短就地反馈，不用整页帮助文案代替真实交互。
- 空状态一行说明加明确入口即可，不讲解整套方法。查询失败不冒充空状态；原始技术诊断放可展开详情，正常页面不渲染 RPC 名称、SQL 或 schema 说明。
- 奖励变化、误完成撤销、兑换金额、未知结果重试、未保存内容放弃等关键确认保留在对应操作时；“减少无关信息”不能成为隐藏安全提示的理由。

默认范围“全部行动”，默认状态“未完成”。从主线或项目进入的范围有清晰标题和“全部行动”返回入口。范围选择只是浏览过滤，不写数据库，也不自动改变关注项目。

关注项目仍由用户明确设置，并在组织层级标记“当前关注”；不再成为其他项目的显示条件。

### 3.2 正式 TODO

工作台与行动页共用同一行动列表和操作组件，始终对应同一个 task ID。

- 默认包含 `todo`、`in_progress`、`waiting`，包含核心与普通、项目与独立行动。
- 可筛选“全部 / 核心 / 普通”和具体状态，不预选核心，不按短平快、奖励或推测重要性排序。
- 未完成但属于已完成/归档项目的行动仍可找到，分组显示“所属项目需恢复”，沿用现有写入限制，不静默丢失。
- done、cancelled 不占默认执行列表，明确的“已完成 / 已取消”历史入口可查看、重开或回看记录。
- 行动显示标题、状态、核心标识、项目归属和可选截止日期；不属于项目时显示“独立行动”，不误标收集箱。
- 所属项目可点击，主线信息通过项目归属得到；没有项目的行动不凭空推断主线。
- 保持数据库返回的确定排序，同创建时间用 ID 打破并列；筛选只改变展示，不改变截止日期、状态或核心资格。
- 未完成计数与当前范围一致，waiting 算未完成，done/cancelled 不算；需恢复项目的事项单独计数且可展开。

切换筛选时更新标题、数量和程序可读的选中状态。原“零散事务”概念改为普通独立行动的可选筛选，不再是默认入口。

### 3.3 组织层级

现有“主线成长”区域改名为“主线与项目”，展示真实主线 → 所属全部项目 → 项目行动，可逐级展开，不另设固定侧栏。关注项目摘要仍可保留，但同一主线卡片必须有查看全部项目和行动的入口。项目名称作为明显的次级标题，可点击进入已有项目详情；折叠/展开用独立按钮，不与详情导航冲突。项目节点显示真实阶段成果进度和未完成行动数，行动节点可打开或完成，操作复用现有确认流程。

没有主线的项目在组织根部显示为“独立项目”，按同一项目节点规范展示并可展开行动；没有此类项目时不画空分组。没有项目的“独立行动”直接保留在下方全局行动清单，不造一条虚假的项目归属。任何正式对象都有可访问入口。归档主线/项目默认可折叠隐藏，但提供显式历史开关；从某条行动回看历史归属时可以显示其历史路径。

每条主线可“添加项目”，每个可写项目可“添加行动”；从该上下文进入表单预填已有主线/项目，用户可修改归属。无有效归属时不自动套用当前关注项目。

展开与选择采用嵌套列表、独立 disclosure 按钮、明确的 aria-expanded/aria-pressed，不靠颜色表达选中，不把一个可点击卡片嵌套多个冲突按钮。不实现拖拽组织、批量改归属或自定义排序。

### 3.4 保留项目管理页

项目页与工作台读取同一批真实项目，不创建第二套对象。工作台给出层级和执行入口；项目页承担平铺查找全部项目、按真实状态筛选及访问已完成/归档历史的职责。每条项目只展示名称、所属主线或独立项目、状态、真实阶段成果进度和必要操作，长说明在详情查看。

点击项目进入既有详情，阶段成果管理、进展、行动、编辑与归档复用现有功能；不在列表再复制一套项目编辑表单。统一“＋新增”继续提供新建项目。此次导航简化不扩大为项目业务规则重做或第二套项目详情设计。

## 4. 统一新增与快速收集

事务 layout 提供所有事务页面可见的 `＋新增`，桌面和手机含义一致。打开统一面板后默认“快速收集”，其他选择是“新建行动 / 新建项目 / 新建主线 / 记录进展”。商店的“添加奖励”保留其上下文入口，不强迫塞进事务捕获流程。

快速收集只有文本和“放入收集箱”按钮；不要求项目、日期、核心资格或奖励条件。一条提交保存一条收集项，本次不自动拆成多条，也不调用 AI。

选择直接创建时复用已有表单、验证和 RPC，不复制第二套业务规则。在项目上下文选择新建行动时预填项目；选择快速收集时不自动确定正式归属。

成功只在数据库确认后反馈，输入框可重新收集下一条，但上一次未知结果不能解锁为新请求。Ctrl/Cmd+Enter 仅在已聚焦的捕获输入中提交；普通 Enter 保留换行，不拦截系统快捷键。

面板支持键盘、Esc、焦点恢复和移动端内部滚动。已经输入但未提交时关闭须明确确认放弃；pending/uncertain 沿用不可变请求和关闭保护，不丢失未确认结果。

## 5. 收集与整理

### 5.0 已选收集箱布局

不重复显示大标题“收集箱”。导航下是轻量多行快速收集输入与“收集”按钮；随后是“待整理 / 已整理 / 已丢弃”筛选。pending 数量保留在收集箱入口及待整理筛选，不新增四项指标、金币规则或方法说明。

桌面采用第二版列表/详情布局：左侧显示收集原文、创建日期及“整理”和次级菜单；选中条目有明确的视觉与程序可读状态。右侧仅在用户选择整理时显示该条目的整理表单，未选择时不常驻空表单或教程。列表保持可见，避免每次整理都离开当前页面。收集项没有任务完成勾选框。

右侧可选择“行动 / 项目”；默认行动，预填标题，项目可为空，默认普通行动。次要字段折叠，核心资格字段仅在明确选择核心后展示并验证；项目模式按下文要求填写名称与预期成果。原文可回看且完整保留，不因为标题限长而截断。

手机与无法保持列表/表单可读宽度的窄屏使用同一整理表单的抽屉，不压缩为两栏；抽屉可内部滚动、键盘操作及恢复焦点。此响应式适配是设计建议，桌面效果稿本身没有验证手机布局。

切换条目、切换整理目标或关闭表单不静默丢弃已修改字段：有未保存修改时确认放弃；pending/uncertain 时冻结原请求与参数，不允许通过切换对象绕过保护。成功后仅在真实数据库确认下移除 pending 条目、更新数量，关闭该次表单；不自动选中下一条并提交、不产生假任务。

### 5.1 独立状态

收集项是未整理的信息，不是已经承诺执行的任务。默认 `pending`，在收集箱按 created_at DESC、id 稳定展示，数量仅统计 pending。

- pending：可编辑原文、整理为行动、整理为项目、丢弃。
- resolved：显示整理目标和链接，原文保留可回看；不再提供再次整理或恢复到 pending。
- discarded：软丢弃，保留记录，可恢复为 pending；不做物理删除。

一个收集项只产生一个目标，本次不支持拆分多个目标、关联已有对象、整理成笔记、主线或自动展开项目任务。长文本完整保留，不能因为正式标题限长而静默截断原文。

### 5.2 整理为行动

预填文本用于标题/说明，用户确认标题（既有上限 200 字）；长原文保留在说明，标题超长时提示编辑，不悄悄裁切。默认普通行动，项目和截止日期可为空。

用户明确选择核心行动时，依然必须填写核心原因和完成条件。不能仅因属于某条主线或项目就自动成为核心。整理后的新行动为 todo，未完成、不发币、不产生贡献。

### 5.3 整理为项目

用户确认名称和预期成果（沿用既有名称 200、成果 2000 字限制）；可选主线、说明和截止日期。原文在说明/来源中保留，新项目 active；不自动创建里程碑或行动，不改变主线关注项目。

整理后收集项退出 pending 列表，但在“已整理”保留目标链接。正式对象后来改名、改归属、归档或完成，原收集记录仍在；目标按真实当前信息展示，不把原文覆盖为新标题。

## 6. 增量数据与原子写入设计

以下是待实现设计，不能视为正式库已经存在。只新增增量 migration，不改已执行的一期 migration；用户仍自行执行正式库 SQL。

新增 `public.affairs_inbox_entries`，至少含：

- id、user_id、created_at、updated_at、revision，遵循一期 owner/revision 口径。
- content：去除首尾空白后 1–4000 个字符，保留内部换行，拒绝非文本类型。
- status：pending / resolved / discarded。
- resolved_task_id、resolved_project_id：分别为 owner 复合外键，不使用无法约束 owner 的多态 UUID。
- resolved_at、discarded_at；状态约束确保 resolved 只存在一个目标，pending/discarded 没有目标；恢复时清除当前 discarded_at，历史丢弃事实仍保留在 commands。

不回填或重命名既有主线、项目、行动；没有项目的既有任务仍是正式行动。新的收集箱初始为空。

拟新增五个 authenticated-only 公共 RPC：

| RPC | 行为 |
| --- | --- |
| create_affairs_inbox_entry | 捕获一条文本 |
| update_affairs_inbox_entry | 编辑 pending 原文，检查 revision |
| resolve_affairs_inbox_entry | 原子创建 task 或 project，并标记收集项 resolved |
| discard_affairs_inbox_entry | pending → discarded，软丢弃 |
| restore_affairs_inbox_entry | discarded → pending |

命令统一使用 request UUID、规范化 payload、owner、revision 和 `affairs_commands`。同请求同规范化参数返回旧回执，不同参数拒绝；不同请求对已 resolved 项再次整理也拒绝，不产生第二个目标。

resolve 的一次事务：验证 Auth/参数 → owner wallet 锁 → 规范化命令重放检查 → 项目按既有顺序锁 → owner 收集项锁 → revision/状态/目标引用验证 → 创建正式对象 → 更新收集项 → 持久化命令回执。任一步失败整笔回滚。

复用现有私有文本、字段白名单、归属和钱包 helpers；不要从客户端分开调用“创建目标”和“标记已整理”，也不要以同一 request UUID 嵌套调用既有公共创建 RPC造成命令冲突。

普通捕获、编辑、丢弃、恢复回执沿用一期 receipt。resolve 回执中 object_id/object_revision 对应收集项，并额外返回 resolved_resource、resolved_object_id；类型与 UI 明确区分目标 ID 和收集项 ID，不破坏旧 RPC 签名。所有新命令 coin_delta=0，返回的 balance 是当次历史回执，不能冒充当前实时余额。

由收集箱产生的任务/项目可回看来源。任务命令历史查询应识别 resolve 命令的目标字段并标注“从收集箱创建”，不能因为 object_id 对应收集项而丢掉该任务的创建事实；同一命令不显示成两条历史。

新表 authenticated 仅 owner SELECT；客户端无直接 INSERT/UPDATE/DELETE，anon/public 无查询或 RPC execute。沿用一期安全约定：受限 SECURITY DEFINER、空 search_path、auth.uid/auth.role 验证、owner 复合外键；不得使用 service_role 或扩大 Finance 的 grants/RLS。

## 7. 数据访问与组件职责

- Server Component → affairs service → typed queries → Supabase SSR client；页面组件不 `.from()`。
- workbench/组织树/行动页复用同一套真实 mainlines/projects/tasks；组织分组只是依据外键，不计算或改变业务进度口径。
- 工作台总览由 service 使用完整任务/项目读取和已有余额 View 得到，携带服务端上海日期边界；与下面的 TODO 范围过滤隔离，不增加逐卡查询或金融业务计算。
- 收集箱 queries 封装真实读取和 pending 数量；adapter 隔离 DB 与 UI，revision 保持十进制字符串避免 bigint 精度丢失。
- 每个 service 创建一个 client，独立读取 Promise.all 并发；不按每个树节点重新查询，不新增全站缓存。
- Server Actions 继续验证 claims，再调用 typed RPC；不依赖未经验证的 getSession，不从浏览器传 user_id。
- 新成功操作只刷新 `/affairs` 相关内容，已部署但浏览器中缓存的列表通过 refresh 更新；不刷新 Finance、不修改其数据。
- Shared QuickAdd 负责入口/上下文，CaptureForm 负责捕获，InboxList/ResolvePanel 负责整理，Outline 负责范围和展开，ActionList 负责正式 TODO；避免将工作台写成新的巨型组件。
- 已有 TaskCompletionPanel、ActionForm、确认面板与业务表单优先复用，但要覆盖连续成功后的新请求生命周期与未知结果冻结，不移除已有安全处理。

## 8. 空状态、错误与兼容

- 没有未完成行动时显示“暂无未完成行动”，提供“快速收集 / 新建行动”，而不是宣称没有全部任务。
- 收集箱没有 pending 时显示“收集箱已清空”，已整理/丢弃仍可从历史进入。
- 查询失败、字段不匹配或 migration 未部署必须显示明确错误；禁止 mock fallback、假金币、假计数和把错误伪装为空。
- revision 冲突提示刷新核对；归属失效提示重新选择；不能自动覆盖用户版本。
- 超时、SDK 传输错误或未知结果保留原 request/payload 重试；刷新或离开须警告，不能自动换 request 新建目标。
- 未部署新增 migration 不得让原商店、金币账本、项目详情等完全无法打开；新增收集箱在对应页面明确报配置错误，统一入口中已有直接创建仍可用。原工作台读取独立于 inbox 新表；收集箱数量不可用时显示“—”，而不是 0。
- 兼容旧路由、既有对象和历史命令；保持暖黑/米白/橙色、字体、组件样式，不改全站主题。不引入新的 UI 包或测试浏览器依赖。

## 9. 验收标准

1. 任意事务页面均可通过统一入口捕获或直接创建，项目上下文的新行动预填项目，未保存时关闭不会静默丢输入。
2. 捕获一句话不需要日期、项目或核心条件；真实保存后收集箱出现一条 pending，TODO 不出现该捕获项。
3. 将 pending 整理成独立普通行动，收集箱 pending −1，TODO +1，原文/目标/命令来源可回看，金币与贡献不变。
4. 整理成核心行动必须满足既有条件，创建不发币；真正完成仍只通过原完成 RPC 发一次 +1。
5. 同请求重复整理、未知结果重试、两台设备以不同请求同时整理，只产生一个目标；旧 revision 不覆盖。
6. 目标写入后、收集状态更新后及命令记录前分别注入失败，全部回滚，不留下“目标已建但收集未整理”。真正并发测试必须使用非正式库多连接；PGlite 单会话不得冒充证据。
7. owner A 不可读取/整理 owner B 的收集项或关联其项目，anon 无权限，authenticated 不能直接写表，全部新命令不影响既有币账与 Finance fixture。
8. 丢弃可恢复，已整理项不能再次恢复/整理；既有无项目普通和核心任务不会被误迁入收集箱。
9. 首页默认可见核心/普通、项目/独立的所有未完成行动；waiting 和需恢复项目的行动不静默消失，完成/取消历史仍可访问。
10. 主线可展开全部项目，项目可展开行动；无主线项目和独立行动有入口；改变浏览范围不写 focus 或复制任务。
11. 阶段成果百分比仍来自现有 View，任务数量/金币不被当作主线或项目进度。
12. 390 / 768 / 1440 检查真实有数据工作台、树、收集箱、整理面板和历史；键盘展开、筛选、焦点回收、关闭保护、滚动按钮及辅助技术选中状态可用。截图不得以 mock 数据假装正式联调。
13. 原一期与 Finance 测试、typecheck、lint、build 均通过；只有用户授权才写正式库、merge/push/deploy。
14. 批注指定的顺序为总览、推进轨迹、主线与项目、行动清单；所有断点保持此顺序，不换成侧栏，也不把 TODO 插在每条主线卡片内部。金币规则从常驻大区块移到按需帮助，不挤占首页。
15. 总览四项不随当前浏览范围变化；waiting/普通/独立/需恢复项目的待办计入，暂停项目不算进行中；近7天完成覆盖上海零点、窗口外/未来时间、任务重开和重复完成，不能用贡献次数替代；金币余额仍来自现有 View。
16. 正常页面不重复方法介绍、技术术语或未上线计时文案；主操作、层级、选中状态、反馈和触屏/键盘入口可理解；减少说明不移除奖励变动、未知结果、放弃输入等必要确认。使用真实数据检查长标题、无日期、等待说明、归档归属、错误与空状态的可读性。
17. 工作台无内容区大标题“事务”；收集箱无重复大标题。收集箱桌面列表/右侧整理面板与已选参考一致，窄屏采用可访问抽屉；未选择对象不展示常驻空表单，切换对象/目标保留未保存与未知结果保护。
18. 顶部导航仅工作台、收集箱、项目、奖励商店、金币记录；工作台“查看全部”仍能进入原完整行动路由及历史，旧收藏链接不失效。主线下项目名称、展开和详情入口易区分，独立项目不遗漏，独立行动不被误挂项目；项目列表和工作台始终指向同一真实对象。
